# Local development and repository preparation

Prepared on **2026-11-06**. This milestone sets up local Terraform scaffolds; it does not implement or deploy AWS resources.

## Pinned tools

| Dependency | Version | How it is enforced |
| --- | --- | --- |
| Terraform CLI | 1.17.1 | Root `.terraform-version` plus exact `required_version` in both Terraform roots |
| hashicorp/aws provider | 6.72.0 | Exact `required_providers` constraint plus `.terraform.lock.hcl` in each root |

Versions were checked against [HashiCorp's Terraform release endpoint](https://releases.hashicorp.com/terraform/1.17.1/) and the [AWS provider registry](https://registry.terraform.io/providers/hashicorp/aws/6.72.0). Use the stable pinned versions, not an unbounded `latest` install. The `.terraform-version` file is a version-manager hint; it does not install Terraform by itself.

Download Terraform from HashiCorp for your OS and compare the archive with its official SHA256SUMS before running it. The Windows AMD64 archive verified for this preparation has SHA-256 `a3b71365cff94c0f978cf75d86addb075ea1bb6409055ea0ab359bf057d7898a`. Other platforms have different archive hashes.

Provider lock files are generated by Terraform from the official registry and release checksums. They include package hashes for Windows AMD64 and Linux AMD64, the local platform and the intended future CI platform. Review the source and version when updating them; never hand-edit hashes.

Each directory under `infra` is a separate Terraform root. `bootstrap` will own the durable state backend; `dev` will own the disposable workload. No shared module directory is needed before there is an implemented boundary worth reusing.

Both roots currently contain provider configuration and local-input declarations, with **no resources or data sources**. The provider's default tags define Project, Environment, and ManagedBy for future resources that support those tags; they are not evidence of existing resources.

## What belongs in Git

Commit configuration, reviewed examples, documentation, the CLI version hint, and both `.terraform.lock.hcl` files. The lock file records provider dependencies and package checksums; it is not a Terraform state file.

The ignore rules exclude `.terraform/`, real `.tfvars` / `.tfvars.json`, real `.tfbackend` files, state and state backups, saved plans, credentials, local tools, and environment files. Example files ending in `.example` remain trackable.

**Keep actual state and saved plans outside the checkout**, even though Git would ignore them. Ignore rules reduce accidental commits; they do not encrypt files, remove already tracked secrets, or prevent someone from explicitly force-adding a file. If a credential is exposed, remove its validity at the source rather than treating a Git deletion as sufficient recovery.

## Local checks for this milestone

No AWS login is required for the following checks. Install Terraform 1.17.1 first. Run these from the repository root in PowerShell. If it is not on PATH, set `$tf` to the absolute path of the verified executable.

```powershell
$tf = "terraform"
& $tf version
& $tf fmt -check -recursive infra

foreach ($root in @("infra/bootstrap", "infra/environments/dev")) {
    & $tf "-chdir=$root" init -backend=false -input=false -lockfile=readonly
    if ($LASTEXITCODE -ne 0) { throw "Dependency initialization failed: $root" }
    & $tf "-chdir=$root" validate
    if ($LASTEXITCODE -ne 0) { throw "Configuration validation failed: $root" }
}
```

`init -backend=false` downloads / installs the pinned provider locally, but does not configure the local or S3 state backend. `validate` checks syntax and provider schemas without verifying deployment against live AWS resources. Internet access is needed for the registry and package downloads unless dependencies are cached. No CI workflow is introduced in this milestone.

See [Terraform init](https://developer.hashicorp.com/terraform/cli/commands/init) and [Terraform validate](https://developer.hashicorp.com/terraform/cli/commands/validate) for the limits of these checks. Do not infer that a passing validate confirms IAM permissions, quotas, AMI availability, or cost coverage.

The offline calculator remains available independently:

```sh
python scripts/estimate_costs.py
```

On Windows AMD64, Terraform 1.17.1 completed format checking, dependency initialization with backends disabled and lock files read-only, and validation of both roots. The examples and provider lock files remained trackable. No AWS service call, plan, apply, backend creation, or resource change was needed for these checks.

## Inputs and authentication

`aws_region` defaults to `us-east-2` and validates against that Region. `aws_profile` defaults to `devops-free`; it is a profile name, not a credential. `terraform.tfvars.example` documents these values. If local overrides are needed later, copy it to an ignored local file, and do not place access keys in it.

AWS service work in a later milestone must use the existing temporary-credential login flow, with any interactive sign-in completed by the human user. Never copy tokens, the AWS login cache, or CLI credential files into this repository. Local fmt, dependency initialization with the backend disabled, and validate do not need a renewed AWS session.

## State setup is the next milestone

`dev/backend.tf` declares a partial S3 backend. Its example configuration deliberately contains a placeholder bucket and must not be used as a real initialization file. Before configuring it, implement and create the backend through a separately reviewed bootstrap procedure.

`bootstrap` deliberately has no backend block yet. **Before adding resources or running its first plan**, explicitly configure a local backend using an absolute state path in a protected location outside this checkout. Never initialize bootstrap with the implicit local-state default. Creating the backend requires a fresh Free-plan / credit / Region check and separate deployment authorization. Migrate bootstrap state to its own S3 key after the bucket exists; use a different key for `dev`.

During repository preparation, do not run `plan`, `apply`, `destroy`, `import`, `refresh`, or state-changing commands. Neither Terraform root is ready to deploy. Backend migration, state recovery, and final cleanup must be documented before using them on real resources.

## Updating dependencies later

Make updates deliberately: update `.terraform-version` and both exact CLI constraints, update both provider constraints, regenerate both lock files, and rerun local checks. Update the documented versions in the same change.

Generate cross-platform hashes with [terraform providers lock](https://developer.hashicorp.com/terraform/cli/commands/providers/lock) for each root:

```sh
terraform -chdir=infra/bootstrap providers lock -platform=windows_amd64 -platform=linux_amd64
terraform -chdir=infra/environments/dev providers lock -platform=windows_amd64 -platform=linux_amd64
```

Add other platforms when needed. The current lock files cover Windows AMD64 and Linux AMD64; they do not claim that this scaffold has been executed on Linux.
